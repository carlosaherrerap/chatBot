 Arquitectura y flujo (resumen rápido)

WhatsApp (Baileys / wweb.js) recibe mensaje de texto.

Worker (Node.js) normaliza mensaje y verifica tipo (solo texto). Si no es texto → ignorar/contestar “sólo texto”.

Si el intent es “consultar deuda” → consulta directa a tu BD/servicio de cobranzas y responde con datos exactos.

Si es consulta libre dentro del dominio (cobranzas):
a. Generar embedding del mensaje (DeepSeek embeddings).
b. Buscar los N fragmentos más relevantes en Redis (vector search).
c. Construir prompt que incluya instrucción “usar SOLO la información recuperada” + fragments + pregunta.
d. Llamar al modelo de generación (DeepSeek ChatCompletion) con ese prompt.
e. Enviar respuesta a WhatsApp.

Si el usuario pide “hablar con asesor humano”: encolar envío de correo con el historial/contexto (nodemailer o servicio SMTP/SendGrid).

Logging/metrics en Redis/DB; errores en un queue para retry.


WhatsApp (Baileys) -> Bot API (Node) -> Task Queue (BullMQ) -> Workers
Workers:
  - Intent router -> (DB query) or (RAG pipeline)
RAG pipeline:
  -> DeepSeek Embedding API
  -> Redis vector search (top-k)
  -> Build prompt
  -> DeepSeek ChatCompletion API
  -> Send reply via Baileys
Human request -> Email sender -> carlos.a.h.palma@gmail.com

Pipeline RAG (Recomendado, sencillo)

Indexación (pre-proceso)

Divide tu “base de contexto” (FAQ, normas de cobro, mensajes típicos, plantillas) en fragmentos (párrafos o oraciones) y anota id, source, texto.

Para cada fragmento, solicita embedding a DeepSeek y guarda {id, embedding, texto, metadata} en Redis (vector index) o en Chroma/FAISS. (Hacer esto una vez o cuando la base cambie).

Consulta en tiempo real (per-message)

Mensaje arrive → crear embedding (DeepSeek).

Buscar top-K (p. ej. 5) en Redis (similaridad coseno).

Construir prompt con una instrucción clara: “Responde solamente utilizando la información marcada a continuación. Si la respuesta no puede determinarse, responde: ‘No tengo información suficiente; solicita hablar con un asesor’.” + fragments.

Llamar DeepSeek ChatCompletion (system+user) para generar la respuesta restringida.

Enviar respuesta por WhatsApp.

Esto mantiene el contexto limitado y evita que el modelo “invente” datos fuera del scope.

Consideraciones de seguridad y privacidad

No enviar PII innecesaria a la API pública (si haces RAG, asegúrate qué fragmentos incluyen datos personales).

Almacena API keys en secrets (K8s Secrets / Vault / .env local solo en dev).

Encriptar en tránsito (TLS) y en reposo (discos).

Consentimiento: informa a usuarios que las respuestas están automatizadas y que sus datos pueden procesarse.

Si quieres máxima privacidad, puedes usar LLM local (Mistral, Llama) para evitar enviar datos a terceros — pero requerirá GPU/infra adicional.

Revisa la política de DeepSeek sobre datos y residencia/retención (hay advertencias en ciertos países); asegúrate que tu uso de datos de deuda cumple regulaciones locales.
